# 2026-09-26 环境排查

## 写后读回失败：原因已确认，修复已部署

原任务导入数值、轮询读回、导入完成标记、再次轮询。每一阶段最多等待 0 + 0.1 + 0.2 + 0.5 + 1 + 1 = 2.8 秒（另加查询耗时）。VM 导入返回 204 只表示接收成功，查询可见性是异步的。

SSH MCP 在真实 VM 上测得（不调用 force_flush）：

| 原表达式 | 数值写入到可见 | 完成标记写入到可见 | 本次完整发布耗时 |
|---|---:|---:|---:|
| DCU CPU | 2.56 s | 4.14 s | 6.75 s |
| DCU Prefill 阶段耗时 | 3.61 s | 4.16 s | 7.90 s |
| A3 Prefill 排队耗时 | 11.75 s | 10.19 s | 22.01 s |

先前失败的六批数值随后全部可见，逐点标签、时间戳和数值与冻结文件一致（rel=1e-9, abs=1e-10）；两批已写完成标记随后也可见。这不是已经证实的数值计算错误，而是发布器把正常可见性延迟当成失败。初始本地 fixture 在写入后强制刷盘，掩盖了时序问题。

修复：持久化每个阶段的已提交时间；暂不可见时抛出单独的等待状态，释放后台执行机会，5 秒后再核验，不重复写入、不重算冻结值、不推进水位。超过 120 秒仍不一致才计为故障并允许按原内容重写。单次执行仍限时 12 秒、全局单并发、最多 60 点。重启复用待处理状态。/health 区分等待与失败，长步长尚未到期的任务不误报积压。

增加了真实 VM、不强制刷盘的重启与异步可见性回归测试，以及部分写入超时后的相同内容重试验证。针对存储/路由的 11 个测试通过。修复镜像在 api-build-v2 中，旧 API 和第一次候选镜像均保留。

## 压测偏差：已定位，正在重新取证

1. 原 page query cohort 把 dashboard 的全部查询按 JSON map 顺序执行，包括未进入 1920×1080 首屏的懒加载面板。例如 backend-performance 首屏实际由 11 条变为 5 条，不能用全页所有面板的顺序请求冒充首屏完成时间。
2. 原非目标探针放在目标请求之后，共用三并发队列。旧版目标请求较多，探针启动时较重的请求往往已结束；新版合并后探针更早启动、与重查询重叠。单独计算探针发起后的 HTTP 耗时，会把不同排队位置导致的竞争差异混进结果。

新测试使用本机原 perf.3 前端捕获的 1920×1080 首屏真实请求集合、步长和顺序，在 SSH MCP 上通过环境 Perses 代理重放。每种缓存模式仍固定窗口、交替 41 对；非目标探针单独执行并与页面同时开始。分别保存页面数据完成与探针服务耗时。属于环境数据性能证据，不宣称浏览器绘制性能。旧报告完整保留；重测结果决定准入，不预先判定通过。
