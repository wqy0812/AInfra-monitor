# vmalert CPU 小范围候选

2026-10-11，延续 [issue #4 可行性评估](vmalert-recording-rules-evaluation.md)。范围是 DCU/XPU 的 CPU 使用率与 iowait，共 4 个面板、7 种步长、28 条记录规则。生产 API 仍创建 `AccelerationService`，本次没有启用候选、修改看板或部署服务。

## 已实现

`monitoring/perses_recording.py`（已删除）提供 `cpu_rules()` 与 `CPURecordingService`。

每条原生规则在**同一次 VM 表达式求值**中返回业务向量以及向量的数量：

```metricsql
WITH (cpu_result = (原表达式)) union(
  label_set(cpu_result, "monitoring_record_kind", "value"),
  label_set((count(cpu_result) or vector(0)), "monitoring_record_kind", "complete")
)
```

它不依赖另外一条心跳或计数规则。业务结果为零条时，仍会写数量为 0 的完成记录；求值报错时，整个规则不产生成功记录。读取侧在原时间格点检查完成数量与业务序列数，齐全才返回；缺值、缺完成记录、重复、异常数值或多份发布结果均保守回源。计数检查不是 remote write 原子性声明，它用于拒绝暂时可见的部分写入。

每次启动或 replay 的结果带独立 `monitoring_record_publication` UUID。同一时刻来自不同进程的值不能互相凑数；重启边界两份发布结果重叠时回源，后续独立格点可以恢复使用原生记录值。规则指标名包含 panel、revision、实际表达式及 step 的身份摘要。

现有 API 继续负责精确表达式/筛选匹配、未知参数回源、最近 60 秒回源、缺口拼接、管理失效、图例排序、相同请求合并，以及**已验证完整封闭窗口**的 30 秒响应缓存。缓存失效仍依赖管理状态；缓存未命中时，记录值查询强制 `nocache=1`，检查当前可见性。原始历史修改前仍须先作废相关区间。

旧 worker 通过一个默认保持原行为的 `manages_materialization()` 接口跳过候选接管的 CPU 任务；DCU/A3 的 98 个原任务不受接管，旧 CPU 水位和待处理证据不删除。候选状态明确将原生任务单独列出，不声称有未经验证的原生水位。

## 运行与证据

```sh
.venv/bin/python --version
pyenv version
.venv/bin/python experiments/vmalert_cpu_candidate.py \
  --output evidence/issue4-cpu-new-run
```

需要本地已有 `victoriametrics/victoria-metrics:v1.151.0` 和 `victoriametrics/vmalert:v1.151.0` 镜像。脚本创建本地临时容器、网络、内存数据目录和 loopback 端口；成功或失败后清理本次容器，保留日志、规则和报告。

加 `--serve` 可保留最多 15 分钟的本地比较页面，也可创建证据目录下的 `stop` 文件提前退出。浏览器版本使用已有 `monitoring-slimming-browser:20261009`（Perses 0.54.0-perf.3），`--plugins` 指定配套插件目录。临时页面只复制受影响 CPU 面板，保留原表达式、图例和插件，布局将两张图并排，不能将其页面耗时当作线上完整主机看板性能。

每次 writer 调用由实验启动器生成新的 UUID 和新规则文件。**不能复用旧配置直接 `docker restart` 或并发启动同一 publication**。生产接入前需要把这项生命周期约束落实到正式启动入口；本次没有自动重启/发布入口。历史修复也不能绕过既有失效流程。

回填起点按所有步长的最小公倍数对齐，避免初次评估发现的 600/3600 秒错位。vmalert 1.151.0 的 `group.maxStartDelay=0` 在本机实测触发除零崩溃，实验使用 `1s`；故障日志保留在首轮证据，不通过修改上游二进制规避。

## 验证范围

- 回归：协议的部分写入、空结果、重叠、非法计数与身份，以及现有调度、水位、管理和就绪测试。
- 真实 VM/vmalert：CPU 的正常、零值、缺样、过期、down、restart、reset、消失、恢复，所有有限筛选，与现有预计算等覆盖对照。
- 故障注入：真实 VM 中缺完成记录、缺值、跨发布写入；原生进程暂停、独立进程恢复、查询 endpoint 失败；未知表达式/步长/参数、非对齐请求、禁用组、作废区间和最近 60 秒。
- 后端诊断：4 面板 × 7 步长 × 2 缓存模式，21 次交替配对。基线是当前预计算，双方使用同一 VM、同一窗口和完整历史覆盖。这是本地探索性采样，不是生产性能准入矩阵。
- 浏览器：本地真实 Perses、1920×1080，比较普通窗口、1 小时窗口、零值、缺样、过期，以及角色筛选、图例、颜色和查询结果。

长步长的故障场景、长期运行资源消耗和生产负载尚未全覆盖；原生进程暂停/恢复的格点验证使用 5 秒步长。保留失败运行，不把配置失败或重启边界的预期回源算成已经通过。

## 结果

最终证据为 [`report.json`](../evidence/issue4-cpu-candidate-20261011-r4/report.json) 和 [`browser.json`](../evidence/issue4-cpu-candidate-20261011-r4/browser.json)。

| 项目 | 结果 |
| --- | --- |
| 相关 Python 回归 | 88 passed |
| 真实 VM 数值、缺口、排序和现有预计算对照 | 208 项通过 |
| catalog 筛选组合 | 252 项通过 |
| 故障与回源检查 | 13 项通过 |
| 1080p 浏览器 | 10 组新旧对照通过，无脚本错误 |

浏览器覆盖两类主机页上的四个 CPU 面板、普通/1 小时/零值/缺样/过期窗口，以及角色筛选、图例和颜色。本次页面实际请求步长均为 5 秒；其他六种步长通过后端检查，不把它们声称为浏览器已覆盖。XPU 当前看板的 Prefill 对应 `xpu-2`，测试读取实际变量配置；未列入旧 catalog 的角色表达式保持回源，两条读取路径结果相同，没有修改角色映射或 catalog。

本地后端采样，每组 21 次交替配对、共 56 组：

| 模式 | 当前预计算 | CPU 候选 | 候选中位数更小的组数 |
| --- | ---: | ---: | ---: |
| 允许响应缓存 | 0.0702 ms | 0.0699 ms | 14 / 28 |
| 绕过响应缓存 | 1.0274 ms | 1.0242 ms | 17 / 28 |

表中延迟是各组中位数的中位数，计时包含本机 Python 读取适配与 VM 请求，不包含浏览器/生产代理链路。差异很小，属于基本持平，不能据此认定更快；这也不是现有 41 次配对的正式准入结果。首个候选曾关闭已验证响应缓存，热查询明显变慢，最终保留原缓存与管理失效语义后重新采样，没有沿用首次性能数据作为最终结果。

候选功能可用，完整性保护已落地，继续迁移的价值主要是让原生组件承担计算调度与回填。CPU 试点阶段保留其他组的旧 worker，仓库代码总量尚未下降。本次不切换生产、不扩展到 DCU/A3、不删除旧预计算；正式接入还需实现每次进程启动自动生成 publication 的部署入口，并在实际负载与相同历史覆盖下评估资源消耗及完整看板性能。

失败证据：首轮原生启动参数触发崩溃；`r2` 误将重启同一格点的预期保守回源判为恢复失败，后改为验证旧进程停下后的新格点；`r3` 的核心验证已通过，浏览器临时镜像因缺插件配置失败。最终 `r4` 补齐插件后完成浏览器验收。最初浏览器脚本硬编码 XPU 节点对应关系导致失败，其日志也保留在 `output/playwright/issue4-cpu*`，随后按当前看板变量重测。
